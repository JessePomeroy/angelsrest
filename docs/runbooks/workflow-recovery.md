# Workflow recovery rollout

These changes span the hub/shared Convex package, shared Admin package, and delivery Worker. They are local implementation until released through the normal package and staging gates. No emails, charges, production writes, credentials, or deployment changes are part of local verification.

## Release order

1. Deploy the additive gallery Worker processing response and deletion tombstones. Processing with `expectedSizeBytes` returns `sizeBytes` and rejects mismatches; older callers remain supported. Keep upload streams and existing capabilities unchanged.
2. Deploy the shared Convex schema/functions and crons. Run `businessRecords:ensureSearch` internally once, or wait for its hourly cron. Its 50-record cursor backfill is resumable and idempotent. Browsing works immediately; search refuses incomplete indexes. New record writers maintain the search text.
3. Configure the purpose-separated notification runner on the matching hub and Convex deployment as described in `tenant-inquiries.md`. Deploy the hub runner and atomic contact intake. Do not enable intake on a host without a working runner. Queued messages remain durable if the runner is temporarily unavailable.
4. Release the additive Admin and CRM packages before changing consumer version ranges. Adopt the capabilities in the hub and test Reflecting Pool with the same packages/backend. Standard client bindings accept these capabilities optionally; explicit capability maps must opt in. Proxy capability maps must not enable unavailable backend modules during a partial rollout.
5. Use an approved accessible staging origin and synthetic records to verify the five workflows below. Do not disable deployment protection or substitute production for staging.

## Behavior and acceptance

- Blog drafts: edit a title, emit another revision, and confirm local edits survive with publication blocked until conflict resolution. Reopen the same tab and recover unsaved work. Navigation warns for unsaved blog, product, and singleton editors. Recovery storage is local to the browser/tab and can be unavailable; the UI reports that and offers draft download. It is not long-term revision history.
- Records: traverse more than 500 orders and 200 invoices/quotes/contracts; filter/search server-side, open an exact older ID, and export every matching cursor page. Exports fail without creating a partial file if paging fails, repeats, or exceeds 50,000 rows/50 MB; narrow filters for larger exports. Search uses indexed word/prefix semantics. Date-filtered search can have empty intermediate pages. Page statistics describe the loaded page, not account-wide totals. Exports are current operational data, not an immutable accounting snapshot.
- Notifications: submit a synthetic inquiry, simulate provider acceptance/rejection/uncertainty and lost completion, and inspect the Admin status. Acceptance means provider acceptance only. Attempts reuse frozen content, one key and one sender fingerprint; never issue a new key to resolve uncertainty. Five automatic attempts, three manual recoveries, a two-minute lease and a [23-hour replay bound](https://resend.com/changelog/idempotency-keys) keep retries finite. Deleting an inquiry also removes its notification envelope. Offboarded/canceled tenants cannot dispatch.
- Uploads: persist the checkpoint before sending bytes, reload after the original is stored, then recover processing and registration without a File object. Verify missing originals and size mismatches do not register. An interrupted byte transfer requires removing the checkpoint and reselecting the file. Explicit remove uses a durable deletion state and Worker tombstone before cleanup, preventing late registration or PUT/multipart resurrection. A gallery with open checkpoints must finish recovery/cleanup before deletion. Browser closure does not continue uploads in the background. Existing browser queues without the capability keep their previous behavior.
- Recurring invoices: existing metadata is inert until explicit activation with today/future first date. Activation snapshots items, tax, notes and client. Each UTC cycle produces one numbered draft atomically, never sends email or creates a payment. Monthly/quarterly/yearly dates clamp short months and retain the original anchor; February 29 maps to February 28 outside leap years; end date is inclusive. Active downtime catches up one cycle per transaction, while pause/resume skips missed dates. Cancel is permanent. Account/client/template loss pauses creation. Template and generated invoice history is retained, including owner erasure's financial-obligation phase.
